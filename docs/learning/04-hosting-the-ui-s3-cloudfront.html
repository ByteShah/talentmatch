4.1Static sites and SPAs

Our UI is a static site: a few files (HTML, JS, CSS) that never change while being served. All the "thinking" happens in the browser (React) or in the API (Lambda). So we don't need a web server, just a place to keep files.

In simple words

A static site is like a printed board game box. The box (files) is the same for everyone. You take it home and play on your own table (the browser). Nobody at the shop has to play along with you. A Single-Page App (SPA) is a game where you never leave the table: going to "/jobs" just rearranges the pieces instead of fetching a new box.

Example: our whole UI is 3 files, about 222 KB (69 KB gzipped).

4.2S3: where the files live

S3 (Simple Storage Service) stores files called objects inside containers called buckets. Each object has a key, its full name like assets/index-laRIqOoM.js. Our web bucket is locked: nobody on the internet can read it directly.

In simple words

A bucket is a locker at school. Objects are the books inside, and the key is the label on each book's spine. "Block public access" means the locker has no window and no spare key, so even if a book fell open, nobody walking past could read it.

lib/talentmatch-stack.ts
const webBucket = new s3.Bucket(this, 'WebBucket', {
  blockPublicAccess: s3.BlockPublicAccess.BLOCK_ALL,   // can never be made public by accident
  encryption: s3.BucketEncryption.S3_MANAGED,          // files encrypted on disk, AWS manages the key (free)
  enforceSSL: true,                                    // refuse plain http:// requests to the bucket
  removalPolicy: cdk.RemovalPolicy.DESTROY,            // cdk destroy deletes the bucket…
  autoDeleteObjects: true,                             // …after a helper Lambda empties it
});

It belongs to the CDKToolkit stack, not to TalentMatch-dev, and every cdk deploy uploads our zips there first. Delete it and the next deploy fails. 4.3CloudFront: the delivery network

CloudFront is AWS's CDN (Content Delivery Network). It keeps copies of our files in hundreds of edge locations worldwide, serves them over HTTPS from the nearest one, and asks S3 only when it doesn't have a copy.

In simple words

S3 is the central warehouse in Mumbai. CloudFront is a chain of corner shops in every city. The first customer in Delhi asks the Delhi shop for index.html. The shop doesn't have it, fetches it from the warehouse (a "miss") and keeps a copy. The next customer gets it straight off the shelf (a "hit"). Faster for everyone, and the warehouse is visited less.

lib/talentmatch-stack.ts
const web = new cloudfront.Distribution(this, 'WebDistribution', {
  defaultBehavior: {
    origin: origins.S3BucketOrigin.withOriginAccessControl(webBucket),   // 4.4
    viewerProtocolPolicy: cloudfront.ViewerProtocolPolicy.REDIRECT_TO_HTTPS,  // http:// → https://
  },
  defaultRootObject: 'index.html',        // "/" means index.html
  errorResponses: [ … ],                    // SPA fallback, 4.5
});
const webUrl = `https://${web.distributionDomainName}`;   // https://d2kcn6pne6ts5i.cloudfront.net
Technical view

A distribution has one or more origins (where files come from) and behaviors (rules per path). Each cached copy lives for its TTL (time to live). The default cache policy keeps files up to 24 hours. When we deploy new files, BucketDeployment sends an invalidation for /*, which tells every edge to drop its copies, so users get the new version. The first 1,000 invalidation paths a month are free, and /* counts as one.

Watch out

The first deploy of a distribution takes 5–10 minutes, because CloudFront has to roll it out to every edge. That's normal, not stuck. Watch it in CloudFormation → TalentMatch-dev → Events.

4.4OAC: the key only CloudFront holds

The bucket is private, so how does CloudFront read it? With Origin Access Control (OAC): CloudFront signs every request to S3, and the bucket policy says "allow reads only if the signer is this distribution".

In simple words

The locker (bucket) has a note taped inside: "Only the school librarian with badge #E2ABC may take books out." CloudFront is that librarian. You, walking up to the locker yourself, have no badge, so the answer is "403 Forbidden". Asking the librarian (the CloudFront URL) works.

CDK writes that policy for you from one line, S3BucketOrigin.withOriginAccessControl(webBucket). In cdk diff it showed up in the IAM table as roughly:

Effect:    Allow
Principal: Service cloudfront.amazonaws.com
Action:    s3:GetObject
Resource:  arn:aws:s3:::talentmatch-dev-webbucket…/*
Condition: AWS:SourceArn = arn:aws:cloudfront::143495498376:distribution/E…   ← only OUR distribution
Technical view

OAC replaced the older OAI (Origin Access Identity). OAC signs requests with SigV4, supports SSE-KMS buckets, and works in all regions. Because the bucket grants only s3:GetObject and not s3:ListBucket, a missing file returns 403 rather than 404. S3 won't even tell an outsider whether a key exists. That detail matters in the next section.

4.5The SPA fallback: making deep links work

Open /jobs/123 and refresh, and the browser asks CloudFront for a file called jobs/123. That file doesn't exist. Our fallback rule says: "when S3 says 403 or 404, send index.html with status 200", and React then reads the URL and shows the right view.

In simple words

You ask the shop for "the page about job 123". The shop has no such sheet, only the one magic book (index.html) that can show any page. So instead of saying "we don't have it", the shop hands you the magic book, and the book opens itself to job 123.

lib/talentmatch-stack.ts
errorResponses: [
  { httpStatus: 403, responseHttpStatus: 200, responsePagePath: '/index.html' },   // OAC hides missing keys as 403
  { httpStatus: 404, responseHttpStatus: 200, responsePagePath: '/index.html' },
],
Watch out

The fallback is global. A typo like /asets/app.js also gets index.html with 200, so a missing JS file can look like "the page loaded but is blank". Check the Network tab: the JS request will show content-type: text/html.

4.6CORS: why the browser blocked us and curl didn't

Our page lives on https://d2kcn6pne6ts5i.cloudfront.net and the API on https://1ezo0amr36.execute-api…. Those are different origins. Browsers won't let a page read a response from another origin unless that server explicitly says "this origin is allowed". That permission system is CORS.

In simple words

The browser is a strict parent. Your page (the kid) wants to talk to a stranger's house (the API). The parent first phones that house (the preflight) and asks: "Is my kid from CloudFront Street allowed to visit?" Only if the house answers "yes, CloudFront Street is welcome" does the visit happen. curl is an adult with no parent, so it just walks in. That's why curl worked and the browser didn't.

lib/talentmatch-stack.ts
const api = new apigw.HttpApi(this, 'HttpApi', {
  apiName: `talentmatch-${props.stage}`,
  corsPreflight: {
    allowOrigins: props.stage === 'dev' ? [webUrl, 'http://localhost:5173'] : [webUrl],
    allowMethods: [apigw.CorsHttpMethod.GET, apigw.CorsHttpMethod.POST],
    allowHeaders: ['content-type'],
  },
});

Notice that the API needs webUrl, so the distribution must be created before the API in the code. In dev we also allow http://localhost:5173 so npm run dev works. Prod allows only the real site.

Real story from our build

Before we added corsPreflight, npm run dev on localhost showed "API error: Failed to fetch". Meanwhile curl $API/v1/health worked perfectly. DevTools → Console told the truth: "blocked by CORS policy: No 'Access-Control-Allow-Origin' header". The request had reached the server. The browser just refused to hand the answer to our JavaScript.

4.7config.json: telling the page where the API is

The API URL only exists after deploy, so it can't be baked into the React build. Instead, CDK writes a small config.json into the bucket at deploy time, and the page fetches it first.

In simple words

You print the game box (the build) before you know which café you'll play in. So you leave a blank sticky note slot. On delivery day, the delivery person (CDK) writes the café's address on the note (config.json). The game reads the note when it opens.

lib/talentmatch-stack.ts
new s3deploy.BucketDeployment(this, 'WebDeployment', {
  destinationBucket: webBucket,
  sources: [
    s3deploy.Source.asset(path.join(__dirname, '..', 'frontend', 'dist'), { exclude: ['config.json'] }),
    s3deploy.Source.jsonData('config.json', { apiUrl: api.apiEndpoint, stage: props.stage }),
  ],
  distribution: web,          // after upload…
  distributionPaths: ['/*'],  // …clear every cached copy
});

Real story from our build

After we destroyed and redeployed, the API got a new ID (1ezo0amr36), but frontend/public/config.json still says h16tw1z5r0, the old one. The deployed site was fine because CDK regenerates its copy. Only localhost breaks. After every fresh deploy, copy the new ApiUrl into the local file.

Watch out

Source.asset('frontend/dist') zips that folder during cdk synth. If dist/ doesn't exist, synth, diff, deploy and even npm test fail with Cannot find asset. Run npm run build in frontend/ first.

4.10Check yourself

Try to answer in your head first, then click to reveal.

Why don't we need a web server for the UI?
The UI is static: after npm run build it's just files (index.html, JS, CSS) that are the same for everyone. All logic runs in the browser or in the API. Storage (S3) plus delivery (CloudFront) is enough.
What's the difference between a bucket, an object and a key?
A bucket is the container (talentmatch-dev-webbucket…), an object is one stored file, and the key is the object's full name inside the bucket, e.g. assets/index-laRIqOoM.js. S3 has no real folders; the slash is just part of the key.
Why is the web bucket private, and what lets CloudFront read it anyway?
Private means nobody can read or leak files directly, and all traffic goes through HTTPS and the CDN. CloudFront reads it through Origin Access Control: it signs requests, and the bucket policy allows s3:GetObject only for cloudfront.amazonaws.com with AWS:SourceArn = our distribution.
Why do we map 403 (not just 404) to index.html?
With OAC, CloudFront may only GetObject, not ListBucket. For a missing key, S3 answers 403 instead of 404, so it doesn't reveal whether the key exists. Without the 403 rule, deep links like /jobs/123 would show an error after refresh.
What does distributionPaths: ['/*'] do, and does it cost money?
After uploading new files, BucketDeployment creates a CloudFront invalidation for every path, so edges drop old copies and serve the new build. /* counts as one path, and 1,000 paths a month are free, so it costs $0.
curl to the API worked, but the browser said "Failed to fetch". Why?
CORS. The page's origin (CloudFront or localhost) differs from the API's origin. Browsers block reading cross-origin responses unless the server sends Access-Control-Allow-Origin for that origin. curl doesn't enforce CORS, because only browsers do.
Why must the CloudFront distribution be created before the HTTP API in our code?
The API's corsPreflight.allowOrigins uses webUrl, which comes from web.distributionDomainName. You can't use a variable before it exists. CloudFormation also gets the dependency order right from that reference.
Why don't we put the API URL into the React code at build time?
The URL only exists after the API is deployed, and it differs per stage and after every fresh deploy. With a runtime config.json written by Source.jsonData, one build works everywhere, and CDK fills in the right URL automatically.
Localhost shows "Failed to fetch" after you destroyed and redeployed, but the CloudFront site works. What's wrong?
The local frontend/public/config.json still has the old API URL (in our case h16tw1z5r0 instead of 1ezo0amr36). The deployed site regenerates its config, but the local file doesn't. Paste the new ApiUrl output into it.
You see npm error Missing script: "test" right after a successful frontend build. What happened?
You were still inside frontend/, whose package.json has no test script. npm only reads the package.json in the current folder. cd .. to the root and run npm test there.
After cdk destroy, a bucket named cdk-hnb659fds-assets-… remains. Should you delete it?
No. It's the CDK bootstrap bucket from the CDKToolkit stack, and every deploy uploads its zips there first. Deleting it breaks cdk deploy until you re-bootstrap. It costs fractions of a cent. Clean old assets with cdk gc if ever needed.
Why does autoDeleteObjects: true exist? What would happen without it?
S3 refuses to delete a bucket that still has objects, so cdk destroy would fail with "bucket not empty". The option adds a custom-resource Lambda that empties the bucket first. We only use it because dev data is disposable.
