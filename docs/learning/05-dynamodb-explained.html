5.1Meet DynamoDB

DynamoDB is a database you never manage. There's no server, no disk and no version to upgrade. You create a table and read and write items, and you pay per request.

In simple words

Picture a huge library run by a very fast librarian. The library is divided into folders. Every folder has a name on the front, like JOB#1, and inside are pages kept in alphabetical order, like APP#cand-a, APP#cand-b and META.

To find something, you tell the librarian the folder name, and optionally which pages. The librarian walks straight to that folder. You never wander the shelves yourself.

Technical view

A table holds items (rows). Each item is a set of attributes (name/value pairs). Only the key attributes are required. Every other attribute is optional, and two items in the same table can have completely different attributes, because there is no fixed schema.

DynamoDB spreads the data over many servers called partitions, so it stays fast whether you have 10 items or 10 billion.

Data types

Every value has a type. The raw AWS API (and the CLI) makes you write the type next to every value. Python's boto3 resource API does that conversion for you.

Type codeMeaningCLI / raw JSONIn Python (boto3)

Watch out: numbers come back as Decimal

boto3 returns every number as Python's Decimal type, so that no precision is lost. But json.dumps(Decimal("90")) crashes with TypeError: Object of type Decimal is not JSON serializable. That's why app.py has a json_default helper that turns Decimal("90") into 90 and Decimal("90.5") into 90.5. Jobs have no numbers yet, but scores will in Sprint 9.

5.2Keys: the partition key and the sort key

Every item is found by its key. The key has two parts: the PK picks the folder and the SK picks the page. Together they must be unique.

In simple words

Think of a school cupboard. The PK is the name on the drawer ("Class 5B"). The SK is the label on each file inside it, and the files are kept in order ("Asha", "Ben", "Chen"). To grab one file you need both: the drawer and the file label.

All the files in one drawer are called an item collection. One trip to one drawer can bring back any range of files from it, like "all files starting with B".

Technical view
  • Partition key (PK, called HASH in the API): DynamoDB hashes it to decide which partition stores the item. Lookups need an exact PK.
  • Sort key (SK, called RANGE): keeps items with the same PK in sorted order, so you can ask for ranges with =, <, >, between and begins_with.
  • The pair PK + SK is the primary key, and it must be unique in the table.
KeyAllowed conditionsWhy
PKOnly = (exact match)Hashed, so similar names end up scattered across partitions
SK= < <= > >= between begins_withStored sorted inside the folder

Our key design for jobs and applications (applications arrive in Sprint 5):

Item typePKSK
JobJOB#<id>META
ApplicationJOB#<id>APP#<candidateId>
CandidateCAND#<id>PROFILE

The JOB# and CAND# prefixes are only a naming convention. To DynamoDB they're plain strings, but they let a human (and your code) see what kind of item each key is.

5.3Why a PK must be an exact match

DynamoDB doesn't store PKs in alphabetical order. It scrambles each one with a hash function and uses the result to choose a partition. So JOB#1 and JOB#2 are not neighbours.

In simple words

Imagine a sorting machine at a post office. Each letter's name goes in, and the machine prints a random-looking bin number: "JOB#1 → bin 7", "JOB#2 → bin 2". The machine always gives the same name the same bin, so finding one letter is instant.

But if you ask "give me every letter whose name starts with JOB#", the machine can't help. Those letters are in bins 7, 2, 11… you would have to open every bin. That's a Scan.

Technical view

A Query's KeyConditionExpression must contain PK = :value. It may also add one condition on the SK. Anything else on the PK, such as begins_with(PK, …) or PK > …, returns ValidationException: Query key condition not supported.

So how do we "list all jobs"? We give every job the same value in a second key, GSI1PK = "JOB", and query that index with an exact match (Section 5.6).

5.4Single-table design

In SQL you make one table per kind of thing and join them together. DynamoDB has no joins. So you put every kind of item in one table, and let the key values say what each item is.

In simple words

SQL is like keeping three separate notebooks, one for jobs, one for candidates and one for applications. To see a job and its applicants, you flip between notebooks and match numbers. That's a "join".

Single-table design is one notebook where a job's page and all its applicants' pages are stapled together in the same folder. One grab gets all of them.

Technical view

Single-table design pre-joins data by giving related items the same PK. The table uses generic attribute names (PK, SK, GSI1PK, GSI1SK), because their meaning depends on the item type. It's the approach in our plan's ADR-004: one table, on-demand billing, and keys chosen for queries we already know about.

The trade-off: ad-hoc questions you didn't plan for (like "every job with 'React' in the description") are hard. The plan accepts this and adds vector search in Sprint 10 for free-text questions.

Single-table designAll item types in one tableJobs, applications and candidates all share our one table
Pre-joiningStoring related items together up frontApplications use the job's PK

5.5The golden rule: access patterns first

In SQL you design the tables first and write any query later. In DynamoDB it's the reverse: list every question the app will ask, then choose keys so each question is one Query or GetItem.

In simple words

Before building a bookshelf, decide how you'll look for books. If you always look by author, put the author's name on each shelf. If you sometimes look by year too, you need a second shelf label: that's an index. Building the shelf first and asking later means re-shelving every book.

#Question the app asksHow the keys answer itSprint
1Get one jobGetItem PK = JOB#<id>, SK = META2a ✅
2List all jobs, newest firstQuery GSI1: GSI1PK = "JOB", sorted by GSI1SK = <createdAt>#<id>, reversed2a ✅
3All applicants for a jobQuery PK = JOB#<id>, SK begins_with "APP#"5
4All jobs a candidate applied toQuery GSI1: GSI1PK = CAND#<id>5
Watch out

Changing keys later is painful. Every existing item must be rewritten with new key values, because keys can't be updated in place. A few minutes with a table like this one saves days of migration.

5.6Global secondary indexes (GSIs)

A GSI is a second copy of your items, organised by different keys. DynamoDB keeps it up to date automatically. It gives you a second way in when the main keys can't answer a question.

In simple words

A school keeps student files sorted by class. The office also keeps a second card box sorted by birthday, so it can find "everyone born in October" quickly. Whenever a student file changes, a helper updates the card box. You never update it yourself. That card box is a GSI.

Three ideas to remember

Overloading

One index answers several questions. Jobs use GSI1PK = "JOB", and applications will use GSI1PK = CAND#<id>. That's why the names are generic.

Sparse

An item is copied into a GSI only if it has the GSI's key attributes. No GSI1PK means it's not in GSI1. You can use this on purpose, e.g. "open jobs only".

Sort by time

GSI1SK = "2026-10-07T09:15…#<id>". ISO dates sort alphabetically in time order, and the #id keeps two jobs from the same microsecond unique.

Technical view
  • A GSI has its own PK (and optional SK) and its own capacity. On-demand billing covers it automatically.
  • Writes to the table are copied to each GSI asynchronously, usually within milliseconds. That's why GSI reads are always eventually consistent (Section 5.10).
  • The projection says which attributes are copied. CDK's default is ALL, so a GSI query returns full items without a second read.
  • A GSI's keys don't need to be unique. Many items can share GSI1PK = "JOB" and even the same GSI1SK.
  • Each write that touches a GSI costs an extra write unit for the copy.

5.7Query vs Scan, and what you pay for

You pay for what DynamoDB reads, not for what it returns. A Query reads one folder; a Scan reads the whole table and then throws away what doesn't match.

In simple words

Ask the librarian for "applications in folder JOB#1" and she walks to one folder and hands you two pages. Ask her to "check every page in the library and give me the applications" and she reads every single page, then gives you the same two. Both times you get 2 pages. The second time she charges you for reading all of them.

How the bill is counted (on-demand mode)

UnitWhat one unit buysRough price
Read request unit (RRU)One strongly consistent read of up to 4 KB, or two eventually consistent reads of up to 4 KB~$0.13–0.15 per million
Write request unit (WRU)One write of up to 1 KB (bigger items use more units)~$0.63–0.71 per million
StorageData kept per month (the first 25 GB are free)~$0.25 per GB

Prices are approximate list prices (us-east-1 low end, Mumbai a little higher). Check the DynamoDB pricing page for current numbers. A Query adds up the size of all items it reads and rounds up to the next 4 KB, so two 1 KB items cost one unit, or half a unit if eventually consistent.

ExampleReadsApprox. cost
1,000 "list jobs" queries, 20 jobs each (~20 KB)~3,000 RRU$0.0004

A filter on a Scan does not save money. It only hides results after they have been read and paid for. One Scan in a popular API endpoint can turn a $1 bill into a four-figure one. Our code never calls scan(), but the permission grantReadWriteData gives the Lambda does allow it (Chapter 6).

5.8Conditional writes and the overwrite trap

put_item means "save this item, replacing anything with the same key". It never warns you. A condition turns it into "save this only if…".

In simple words

Imagine a locker room with no locks. If you put your bag in locker 7, and someone else puts their bag in locker 7, your bag silently disappears. A condition is a sticky note on the door: "only put a bag here if the locker is empty". If the locker is taken, you're told "no", and the first bag stays safe.

Technical view
  • attribute_not_exists(PK) checks whether an item with this exact PK + SK already exists. It doesn't check other items in the folder.
  • The check and the write happen atomically: there's no gap where another writer could sneak in.
  • A failed condition still costs a write unit.
  • jobs.py uses it in create_job as a safety net. A random UUID clash is extremely unlikely, but never overwriting is the right default.
  • In 2b you'll use the opposite, attribute_exists(PK), so that updating a job that doesn't exist fails instead of quietly creating a half-empty item.

Technical terms

5.9Pagination

DynamoDB returns at most Limit items, plus a bookmark called LastEvaluatedKey. You send the bookmark back as ExclusiveStartKey to get the next page. Our API wraps the bookmark as an opaque nextToken.

In simple words

Reading a long book one chapter at a time, you put a bookmark where you stopped. Next time you hand the bookmark back and say "continue from here". When there's no bookmark, the book is finished. A bookmark is better than "page 2", because if someone adds a page at the front while you're reading, "page 2" changes, but your bookmark still points to the exact spot.

Technical view
  • LastEvaluatedKey is the key of the last item read, e.g. {"PK": "JOB#…", "SK": "META", "GSI1PK": "JOB", "GSI1SK": "2026-…#…"}.
  • encode_token() turns it into JSON and then URL-safe base64, so it fits in a query string. decode_token() reverses it, and a garbage token returns 400 BAD_REQUEST.
  • A page can contain fewer than Limit items and still have a next page. Always loop until there's no token.
  • If the last page is exactly full, DynamoDB may still return a LastEvaluatedKey, and the following page comes back empty with nextToken: null. That's normal.
  • Each Query also stops at 1 MB of data read, even if Limit isn't reached.
Watch out

base64 is encoding, not encryption. Anyone can decode a nextToken and see your key layout. "Opaque" means "please don't depend on what's inside", not "secret". Never put private data in a key.

5.10Eventual vs strong consistency

DynamoDB keeps three copies of your data. A write lands on one copy first and reaches the others a few milliseconds later. An "eventually consistent" read may hit a copy that hasn't caught up yet.

In simple words

A teacher writes the homework on the main board, and a helper copies it onto two side boards a moment later. If you glance at a side board during that moment, you might see yesterday's homework. Ask the teacher directly (a strong read) and you always see today's. It takes a bit more effort, so it costs double.

Eventually consistent (default)Strongly consistent
How to askDefaultConsistentRead=True / --consistent-read
Cost½ unit per 4 KB1 unit per 4 KB
FreshnessUsually fresh within ~1 secondAlways the latest write
Available on GSIs?Yes (the only option)No
What this means for TalentMatch

If a recruiter creates a job and the list refreshes in the same millisecond, the new job might be missing for a moment, because the list reads GSI1 and GSI reads are eventual. That's acceptable for an HR tool. In Sprint 2c's UI work, we'll add the newly created job to the list on the screen straight from the POST response, so the user never notices.

5.11Limits: hot partitions, item size, billing modes

Three limits shape our design. Each partition has a speed limit, an item can't be bigger than 400 KB, and you choose how you're billed.

Hot partitions

In simple words

A school has ten doors, but everybody uses door 1 because it's labelled "JOB". At home time there's a queue at door 1 and nobody at doors 2–10. That door is a hot partition. Fix it by labelling doors "JOB-0" to "JOB-9" and spreading people out.

Technical view

Each partition handles roughly 3,000 read units and 1,000 write units per second. Every job shares GSI1PK = "JOB", so all job writes land on one GSI partition. A company creates maybe a few jobs a day, about a million times below the limit, so the simple design wins. Only a platform with millions of job writes per second would need sharding (JOB#0…JOB#9) or time buckets (JOB#2026-10).

The 400 KB item limit

One item, all attributes included, can be at most 400 KB. Our job description is capped at 20,000 characters, around 20–80 KB depending on the characters, so jobs fit easily. Resumes are PDF files of up to 5 MB, so they don't go in DynamoDB. They go in S3 (Sprint 5), and the DynamoDB item stores only the S3 key.

5.12The lab: a throwaway table

Before writing any code, you created a table called lab-s2 with the CLI and felt every rule above for yourself. It cost nothing and took 10 minutes.

  1. Check you're logged in. 
    $ aws sts get-caller-identity
{ "Account": "143495498376", "Arn": "arn:aws:iam::143495498376:user/jaimin-admin" }
  2. Command 1: create the table with only PK and SK, on-demand. 
    $ aws dynamodb create-table --table-name lab-s2 \
    --attribute-definitions AttributeName=PK,AttributeType=S AttributeName=SK,AttributeType=S \
    --key-schema AttributeName=PK,KeyType=HASH AttributeName=SK,KeyType=RANGE \
    --billing-mode PAY_PER_REQUEST
{ "TableDescription": { "TableName": "lab-s2", "TableStatus": "CREATING", ... } }
$ aws dynamodb wait table-exists --table-name lab-s2
# waits silently until the status is ACTIVE

    Notice: HASH = PK and RANGE = SK. PAY_PER_REQUEST = on-demand, so there's no idle cost.

  3. Command 2: add one job, two applications and a second job. 
    $ aws dynamodb put-item --table-name lab-s2 --item '{"PK":{"S":"JOB#1"},"SK":{"S":"META"},"title":{"S":"Odoo Developer"}}'
$ aws dynamodb put-item --table-name lab-s2 --item '{"PK":{"S":"JOB#1"},"SK":{"S":"APP#cand-a"},"score":{"N":"90"}}'
$ aws dynamodb put-item --table-name lab-s2 --item '{"PK":{"S":"JOB#1"},"SK":{"S":"APP#cand-b"},"score":{"N":"49"}}'
$ aws dynamodb put-item --table-name lab-s2 --item '{"PK":{"S":"JOB#2"},"SK":{"S":"META"},"title":{"S":"React Developer"}}'
# each prints nothing on success

    Notice: every value carries its type (S, N), and the job and application items have different attributes. That's schemaless.

  4. Command 3: Query access pattern #3, all applicants for job 1. 
    $ aws dynamodb query --table-name lab-s2 \
    --key-condition-expression "PK = :pk AND begins_with(SK, :app)" \
    --expression-attribute-values '{":pk":{"S":"JOB#1"},":app":{"S":"APP#"}}'
{ "Items": [ {...APP#cand-a...}, {...APP#cand-b...} ],
  "Count": 2,
  "ScannedCount": 2 }
  5. Command 4: Scan the same question the expensive way. 
    $ aws dynamodb scan --table-name lab-s2 --filter-expression "begins_with(SK, :app)" \
    --expression-attribute-values '{":app":{"S":"APP#"}}'
{ "Items": [ ...same 2 items... ],
  "Count": 2,
  "ScannedCount": 4 }

    Notice: ScannedCount: 4. All four items were read and paid for, and two were thrown away.

  6. Command 5: try to query without an exact PK. 
    $ aws dynamodb query --table-name lab-s2 \
    --key-condition-expression "begins_with(PK, :j)" \
    --expression-attribute-values '{":j":{"S":"JOB#"}}'
An error occurred (ValidationException) when calling the Query operation:
Query key condition not supported

    Notice: PKs are hashed (Figure 5.2), so Query refuses.

  7. Command 6: the overwrite trap. 
    $ aws dynamodb put-item --table-name lab-s2 --item '{"PK":{"S":"JOB#2"},"SK":{"S":"META"},"title":{"S":"OOPS"}}'
$ aws dynamodb get-item --table-name lab-s2 --key '{"PK":{"S":"JOB#2"},"SK":{"S":"META"}}'
{ "Item": { "PK": {"S": "JOB#2"}, "SK": {"S": "META"}, "title": {"S": "OOPS"} } }
# React Developer is gone, with no warning
  8. Command 7: the same put, with a condition. 
    $ aws dynamodb put-item --table-name lab-s2 \
    --item '{"PK":{"S":"JOB#2"},"SK":{"S":"META"},"title":{"S":"OOPS again"}}' \
    --condition-expression "attribute_not_exists(PK)"
An error occurred (ConditionalCheckFailedException) when calling the PutItem operation:
The conditional request failed
# nothing changed; "OOPS" is still there
  9. Command 8: clean up (lab rule: delete the same day). 
    $ aws dynamodb delete-table --table-name lab-s2
$ aws dynamodb list-tables
{ "TableNames": [ "TalentMatch-dev-Table…" ] }  # or [] if dev is destroyed
Watch out: quoting in zsh

The JSON is inside single quotes so that zsh doesn't touch the ", { or # characters. If you get Error parsing parameter, a quote is usually missing or curly.

Things we haven't done yet that will deepen your understanding. Each takes under 5 minutes, and all are free at this size. Run them while TalentMatch-dev is deployed and has a few jobs.

Explore more
  • See the real cost of a read. Add --return-consumed-capacity TOTAL to a query and compare a GetItem, a Query and a Scan:

{ "TableName": "TalentMatch-dev-...", "CapacityUnits": 0.5 }
  • Strong vs eventual. Run a get-item with and without --consistent-read and --return-consumed-capacity TOTAL. The strong read shows double the units (1.0 vs 0.5). Then try --consistent-read on the GSI1 query and read the error.
  • The console item editor. DynamoDB → Tables → your table → Explore table items → open a job → JSON view. Switch "View DynamoDB JSON" on and off to see the {"S": …} wrappers that boto3 hides.
  • PartiQL (SQL-like syntax). Console → PartiQL editor: SELECT * FROM "TalentMatch-dev-Table…" WHERE PK = 'JOB#…'. Then try WHERE title = 'Odoo Developer' and notice that it becomes a Scan, because title isn't a key.
  • CloudWatch metrics. Table → Monitor tab: ConsumedReadCapacityUnits, ConsumedWriteCapacityUnits and ThrottledRequests. Create 5 jobs with curl and watch the write graph move (it can take a minute or two).
  • Prove the sparse index. In the console, add a new item PK=TEST#1, SK=META with no GSI1PK. Call GET /v1/jobs. It isn't listed. Add GSI1PK = JOB and GSI1SK = 2099-01-01#x and it appears at the top. Delete it afterwards.
  • Decode a nextToken. echo '<token>' | base64 -d (add = padding if it complains). You'll see your keys in plain JSON. That's why "opaque" doesn't mean "secret".
  • Table settings. Table → Additional settings: find point-in-time recovery (off now; Sprint 14 turns it on), deletion protection, and the table class.

5.15Check yourself

Try to answer in your head first, then click to reveal.

What two parts make up a DynamoDB primary key here, and which must be unique?
The partition key (PK) and the sort key (SK). The combination PK + SK must be unique. Many items can share a PK (an item collection), as long as their SKs differ.
Why can't a Query use begins_with on the partition key?
PKs are hashed to choose a partition, so similar names are scattered across servers. Finding "all PKs starting with JOB#" would mean reading every partition, which is a Scan. Query only allows PK = value.
A Scan reads 10,000 items and returns 5. How many do you pay for?
All 10,000. You pay for ScannedCount, what was read. The filter only removes items after they've been read.
How does TalentMatch list all jobs if a PK must be exact?
Every job gets GSI1PK = "JOB" and GSI1SK = "<createdAt>#<id>". list_jobs queries index GSI1 with GSI1PK = "JOB" (an exact match) and ScanIndexForward=False for newest first.
What is a sparse index, and what happens if a job is saved without GSI1PK?
A GSI only contains items that have its key attributes. A job without GSI1PK is still in the main table (get_job finds it) but is never copied into GSI1, so "list jobs" doesn't show it.
What does index overloading mean? Give our example.
Using one index for several item types and questions. GSI1 holds jobs under GSI1PK = "JOB" and, from Sprint 5, applications under GSI1PK = CAND#<id>, for "all jobs this candidate applied to".
Why must GSI1SK start with the timestamp rather than the job ID?
The sort key sets the order. ISO timestamps sort alphabetically in time order; random UUIDs don't. With the time first, the index is in creation order, and reversing it gives newest first. The #id on the end keeps it unique.
What does put_item do if an item with the same key already exists, and how do we stop that?
It silently replaces it. Adding ConditionExpression="attribute_not_exists(PK)" makes DynamoDB refuse with ConditionalCheckFailedException if the key is taken. The check and the write are atomic.
Why does our API return a nextToken instead of ?page=2?
DynamoDB has no page numbers. It continues from a key, using LastEvaluatedKey and ExclusiveStartKey. A bookmark also stays correct when new jobs are added at the front, whereas "page 2" would shift. Wrapping the key in an opaque token hides our key layout from clients.
When does the list end?
When DynamoDB returns no LastEvaluatedKey, so our API returns nextToken: null. A page can have fewer items than the limit and still have a next page, so clients should check the token, not the count.
Can a GSI query be strongly consistent? What does that mean for "create then list"?
No. GSI reads are always eventually consistent. A job created a millisecond ago might be missing from the list briefly. The UI handles this by adding the new job from the POST response.
Why is GSI1PK = "JOB" fine for us but a problem at huge scale?
All jobs share one GSI partition, which handles roughly 1,000 writes per second. A company writing a few jobs a day is nowhere near that. Millions of writes per second would throttle, and you'd shard the key (JOB#0…JOB#9) or bucket it by month.
Why are resumes stored in S3 and not in DynamoDB?
A DynamoDB item can be at most 400 KB, and resumes can be up to 5 MB. S3 also costs much less per GB. The DynamoDB item stores only the resume's S3 key and the extracted profile.
Why does the plan use on-demand instead of provisioned capacity?
On-demand costs nothing while idle and scales instantly with no planning, which suits a new, spiky POC under a $15 budget. Provisioned is cheaper only for steady, predictable, high traffic, and it charges even when idle.
