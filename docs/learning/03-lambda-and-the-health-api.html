3.1What "serverless" means

Serverless means you hand AWS your code and it runs it only when someone needs it. You never rent, start or patch a machine, and you pay nothing while nobody is calling.

In simple words

A normal server is like owning a food truck: you pay for the truck, fuel and parking every day, even when no customers come. Serverless is like a kitchen that cooks only when an order arrives. Someone orders a pizza, a cook appears, makes it, and goes home. You pay per pizza, and zero pizzas means zero cost.

Tiny example: our health check was called maybe 50 times on test day. Lambda gives 1,000,000 free calls a month, so the cost was $0. A small always-on server would cost about $8–15 a month even if nobody called it.

Technical view

AWS Lambda is a Function-as-a-Service platform. You upload a code package and say which function to call (the handler). AWS keeps a pool of tiny isolated micro-VMs (Firecracker). When an event arrives, it puts your code in one, calls the handler, and later throws the micro-VM away. Billing is per request ($0.20 per million) plus GB-seconds (memory × duration, rounded up to 1 ms).

3.2Handler, event and context

Every Lambda is one function that receives two things, an event (what happened) and a context (facts about this run), and returns an answer.

In simple words

Think of a post office counter. The event is the letter you hand in: who it's from, what it asks. The context is the receipt slip the post office staples on: a tracking number and how much time is left before closing. The handler is the clerk who reads the letter and hands back a reply.

Technical view

The handler string app.handler means "import module app (the file app.py) and call its function handler". For HTTP API (payload format 2.0) the event carries routeKey, rawPath, headers, queryStringParameters, pathParameters, body and isBase64Encoded. The return value must be a dict with statusCode, optional headers, and body as a string, which is why we call json.dumps.

Here is the real code from our project. The handler reads routeKey, logs it with the request ID, and looks the route up in a dictionary:

src/api/app.py
def handler(event, context):
    route = event.get("routeKey", "")                 # e.g. "GET /v1/health"
    log("INFO", "request", context, route=route)      # context gives us aws_request_id
    try:
        route_fn = ROUTES.get(route)                     # pick the Python function for this route
        ...
        status, body = route_fn(event)
        return response(status, body)

def health(event):
    return 200, {"status": "ok", "stage": STAGE, "version": VERSION,
                 "time": datetime.now(timezone.utc).isoformat()}

def response(status, body):
    return {"statusCode": status,
            "headers": {"content-type": "application/json"},
            "body": json.dumps(body, default=json_default)}   # body must be a string
Watch out

Route functions return a pair (status, body); only handler builds the full response dict. In our build, health once returned response(...) instead of 200, {...}. Unpacking a 3-key dict into two variables crashed, the crash was swallowed, and the test showed 404 != 200. Chapter 7 tells the whole story.

3.3The Lambda lifecycle: cold and warm starts

The first request after a quiet period is slower, because AWS has to set up a fresh environment (a cold start). Later requests reuse it and are fast (warm starts).

In simple words

A cold start is like the first coffee of the morning at a café: someone has to switch on the machine, grind beans and warm the milk. That takes a minute. The second coffee is quick because the machine is already hot. If nobody orders for a long time, the machine gets switched off again, and the next customer waits for the warm-up.

Technical view

The lifecycle has three phases. Init: download the code, start the runtime, run module-level code. Invoke: call the handler. Shutdown: after some idle minutes (not guaranteed), the environment is destroyed. Between invokes the environment is frozen, so global variables survive. Each concurrent request needs its own environment, so 10 simultaneous requests can mean 10 cold starts.

Try it: see a cold start in the logs

  1. Deploy, then call the API twice in a row. The first call after a deploy is always cold, because a deploy replaces the code. 
    $ API=https://1ezo0amr36.execute-api.ap-south-1.amazonaws.com
$ curl -s $API/v1/health
{"status": "ok", "stage": "dev", "version": "0.1.0", "time": "2026-10-07T04:12:09.512+00:00"}
$ curl -s $API/v1/health
  2. Read the REPORT lines. Lambda writes one after every invocation. 
    $ aws logs tail /talentmatch/dev/api --since 5m | grep REPORT
REPORT RequestId: 8f1c… Duration: 4.12 ms  Billed Duration: 5 ms  Memory Size: 256 MB  Max Memory Used: 41 MB  Init Duration: 187.40 ms
REPORT RequestId: 2b7a… Duration: 1.95 ms  Billed Duration: 2 ms  Memory Size: 256 MB  Max Memory Used: 41 MB
# The first line has "Init Duration" = cold start. The second doesn't = warm.

Your exact numbers will differ. What matters is that Init Duration appears only on the first line.

3.4Lambda settings, line by line

Six settings in our stack decide how the function runs: runtime, architecture, handler, code, memory and timeout. Two more control what it can see (environment variables) and what it may do (the execution role).

In simple words

Setting up a Lambda is like packing a lunch box for school. Runtime is the language the teacher speaks (Python). Memory is how big the lunch box is: bigger also means a faster helper. Timeout is when the lunch break ends. Environment variables are the note from mum ("you're in class dev"). The role is the permission slip that says which rooms you may enter.

lib/talentmatch-stack.ts
const apiFn = new lambda.Function(this, 'ApiFunction', {
  runtime: lambda.Runtime.PYTHON_3_12,          // language + version AWS starts
  architecture: lambda.Architecture.ARM_64,     // Graviton CPU, ~20% cheaper than x86
  handler: 'app.handler',                       // file app.py, function handler
  code: lambda.Code.fromAsset(path.join(__dirname, '..', 'src', 'api')),  // zip the WHOLE folder
  memorySize: 256,                              // MB; CPU power grows with memory
  timeout: cdk.Duration.seconds(10),            // stop runaway code after 10 s
  logGroup: apiLogs,                            // where print/logger output goes (3.5)
  environment: { STAGE: props.stage, APP_VERSION: '0.1.0', TABLE_NAME: table.tableName },
});
SettingOur valueWhy this valueDefault

Real story from our build

"Does fromAsset make one Lambda per file?" No. fromAsset('src/api') just zips the whole folder: app.py, jobs.py and errors.py all go into the same zip. The new lambda.Function(...) line is what creates a Lambda, so one new means one Lambda. That's why app.py can simply import jobs.

The execution role: CDK makes it for you

A Lambda can do nothing in AWS unless its execution role allows it. When you write new lambda.Function, CDK quietly creates an IAM role (ApiFunction/ServiceRole) that only allows writing logs. Later, table.grantReadWriteData(apiFn) adds DynamoDB permissions to that same role (Chapter 6).

Technical view

The role has a trust policy saying "the service lambda.amazonaws.com may assume me", plus the managed policy AWSLambdaBasicExecutionRole (CloudWatch Logs). Each invocation gets temporary credentials for this role, and boto3 picks them up automatically. That's why our Python code never contains access keys.

3.5CloudWatch Logs: where your prints go

Everything your Lambda logs lands in a log group, split into log streams (roughly one per execution environment). We gave ours a fixed name, /talentmatch/dev/api, and a 7-day retention.

In simple words

A log group is a diary book for one app. Each log stream is one chapter written by one cook in the kitchen (one execution environment). Every line has a time and a request ID, like an order number, so you can find exactly what happened to one customer's order.

src/api/app.py
def log(level, message, context, **fields):
    entry = {"level": level, "message": message, "request_id": context.aws_request_id, **fields}
    logger.log(getattr(logging, level), json.dumps(entry))   # one JSON object per line = "structured log"

Why JSON and not plain text? Because CloudWatch Logs Insights can then filter on fields, like "show me every WARNING with code NOT_FOUND". Plain text can only be searched as text.

Real story from our build

We ran aws logs tail /aws/lambda/TalentMatch-dev-ApiFunctionCE271BD4-BOKH6CBsHL7G --follow and got ResourceNotFoundException: The specified log group does not exist. The command was fine. The name was wrong. We had created our own LogGroup (for 7-day retention) without a name, so CloudFormation invented one like TalentMatch-dev-ApiLogs3D05D88B-AbC123, and the Lambda was writing there, not to /aws/lambda/….

Fix: give it a predictable name and print it as an output.

const apiLogs = new logs.LogGroup(this, 'ApiLogs', {
  logGroupName: `/talentmatch/${props.stage}/api`,   // dev and prod never clash
  retention: logs.RetentionDays.ONE_WEEK,
  removalPolicy: cdk.RemovalPolicy.DESTROY,
});
new cdk.CfnOutput(this, 'ApiLogGroup', { value: apiLogs.logGroupName });
Watch out

aws logs tail only shows events that already exist. Right after a deploy with no requests, it's empty, which doesn't mean it's broken. Run --follow in one terminal tab and curl in another.

Try it

  1. Find the log group from the stack, so you never have to guess. 
    $ aws cloudformation describe-stacks --stack-name TalentMatch-dev \
    --query "Stacks[0].Outputs[?OutputKey=='ApiLogGroup'].OutputValue" --output text
/talentmatch/dev/api
  2. Follow it live (tab 1), then make requests (tab 2). 
    $ aws logs tail /talentmatch/dev/api --follow
2026-10-07T04:12:09 {"level": "INFO", "message": "request", "request_id": "8f1c…", "route": "GET /v1/health"}
  3. Check retention is really 7 days. 
    $ aws logs describe-log-groups --log-group-name-prefix /talentmatch \
    --query 'logGroups[].[logGroupName,retentionInDays]' --output text

3.6API Gateway: the front door

API Gateway gives our Lambda a public HTTPS address. It matches each request to a route and passes it through an integration to the function. We use the cheaper HTTP API type.

In simple words

API Gateway is the receptionist of a building. You walk in and say "GET /v1/health". The receptionist checks the list of allowed requests (the routes). If yours is on the list, they phone the right office (the Lambda). If it isn't, they say "Not Found" themselves and never disturb the office.

lib/talentmatch-stack.ts
const api = new apigw.HttpApi(this, 'HttpApi', { apiName: `talentmatch-${props.stage}`, corsPreflight: {…} });
const integration = new HttpLambdaIntegration('ApiIntegration', apiFn);   // made once…
api.addRoutes({ path: '/v1/health',       methods: [apigw.HttpMethod.GET], integration });   // …shared by all
api.addRoutes({ path: '/v1/jobs',         methods: [apigw.HttpMethod.GET, apigw.HttpMethod.POST], integration });
api.addRoutes({ path: '/v1/jobs/{jobId}', methods: [apigw.HttpMethod.GET], integration });

Each addRoutes quietly creates three CloudFormation resources. You saw them in cdk diff:

ResourceWhat it isWhat breaks without it
AWS::ApiGatewayV2::RouteThe entry "GET /v1/health" on the receptionist's list404 Not Found
AWS::ApiGatewayV2::IntegrationThe phone line to the LambdaThe route has nowhere to send the request
AWS::Lambda::PermissionThe Lambda saying "API Gateway may call me"500 error, a classic mistake in hand-written CloudFormation

The API also gets a $default stage with auto-deploy. That's why our URL has no /prod or /dev at the end. We separate environments with whole stacks instead.

curl -i -X POST $API/v1/health returned 404 {"message":"Not Found"}, and our log tail showed nothing. That's the clue: the message isn't in our error format ({"error": {"code": …}}), so our code never ran. Only GET was registered for /v1/health, so API Gateway rejected the request at the door.

In simple words

3.8Explore more

Things we haven't looked at yet. Each takes 2–5 minutes and teaches you something real.

Explore more
  • Lambda console → your function → Monitor tab. See the Invocations, Duration and Error count graphs that CloudWatch draws for free.
  • Logs Insights (CloudWatch → Logs Insights → choose /talentmatch/dev/api). Count requests per route: 
    fields route
| filter level = "INFO"
| stats count() as requests by route
| sort requests desc
  • Find every cold start in Logs Insights: 
    filter @type = "REPORT" and ispresent(@initDuration)
| stats count() as coldStarts, avg(@initDuration) as avgInitMs
  • Test from the console: Lambda → Test → create an event {"routeKey": "GET /v1/health"}. Your handler runs without API Gateway at all, which proves the event is just a dict.
  • Change memory to 128 MB in the stack, deploy, and compare Duration and Init Duration in REPORT lines. Then set it back. Less memory also means less CPU.
  • Look at the role: IAM → Roles → search ApiFunctionServiceRole. Read the trust policy ("Trust relationships") and the attached policies.
  • See the asset zip: ls cdk.out/asset.* after npx cdk synth. One folder contains your three .py files, exactly what Lambda receives.
  • API Gateway console → your API → Routes: click a route and see its integration. Then open Stages → $default and look at the default throttling limits.

3.9Check yourself

Try to answer in your head first, then click to reveal.

What does the handler string app.handler mean?
Import the module app (the file app.py inside the zip) and call its function named handler. Rename the Python function, and you must change this string in the stack too.
What happens during a cold start, and how do you see one?
AWS creates a new execution environment: it downloads your zip, starts Python and runs the top-level code of app.py (imports, logger setup). Only then does it call the handler. You see it as Init Duration: … ms on the REPORT log line. Warm invocations don't have that field.
Why do we create the DynamoDB connection outside the handler (cached in _table)?
Code outside the handler runs once per environment, during init. Code inside runs on every request. Creating the connection once and reusing it across warm invocations saves time and money on every request after the first.
Our src/api folder has three Python files. How many Lambdas does fromAsset('src/api') create?
Zero. fromAsset only says what code to zip and upload. The new lambda.Function(...) call creates the Lambda, so one call means one function containing all three files. That's why app.py can import jobs.
Why did aws logs tail /aws/lambda/TalentMatch-dev-ApiFunction… fail with "log group does not exist"?
We passed our own LogGroup to the Lambda (to set 7-day retention) without naming it, so CloudFormation generated a name like TalentMatch-dev-ApiLogs3D05D88B-…. The Lambda wrote there, not to the default /aws/lambda/<name>. We fixed it with logGroupName: `/talentmatch/${props.stage}/api` and an output.
Why does the log group name include ${props.stage}?
Log group names must be unique in a region. Dev and prod live in the same account and region, so a fixed name like /talentmatch/api would make the second stack's deploy fail. With the stage in it you get /talentmatch/dev/api and /talentmatch/prod/api.
curl -X POST $API/v1/health returns {"message":"Not Found"}. Did our Lambda run? How can you tell?
No. Two clues: the body isn't in our error format ({"error": {"code": …}}), and the log tail shows no new line. Only GET is registered for /v1/health, so API Gateway rejected the request before calling the Lambda.
What three resources does one api.addRoutes create, and which one causes a 500 if missing?
A Route, an Integration, and a Lambda Permission. Without the permission, API Gateway is not allowed to invoke the function and returns a 500. CDK adds it for you; hand-written CloudFormation often forgets it.
Why does the event say "GET /v1/jobs/{jobId}" instead of the real ID?
routeKey is the route's template, which is exactly what makes our ROUTES dictionary lookup work. The real value is in event["pathParameters"]["jobId"]. The name jobId comes from {jobId} in the CDK path.
Why did we pick HTTP API instead of REST API?
It's about 70% cheaper (~$1 vs ~$3.50 per million requests), adds less latency, and has a built-in JWT authorizer, which we need for Cognito in Sprint 3. We don't need REST-only extras like API keys, usage plans or response caching.
Who gives the Lambda permission to write logs, and where are its AWS credentials?
CDK auto-creates an execution role with the basic execution policy (write to CloudWatch Logs). Lambda gives each invocation temporary credentials for that role, and boto3 finds them automatically. There are never access keys in our code.
Why does the body we return have to go through json.dumps?
API Gateway expects body to be a string. json.dumps turns our Python dict into a JSON string. The default=json_default part converts DynamoDB Decimal numbers, which json.dumps can't handle by itself.
