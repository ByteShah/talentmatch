0.1What we are building

TalentMatch is an internal HR app. It reads resumes, notes every skill with the line that proves it, and ranks candidates against a job with a score anyone can check.

In simple words

Imagine a teacher choosing players for a cricket team. 300 students hand in forms saying what they can do. The teacher has to read every form, decide who really can bowl, and pick the best 11.

TalentMatch is a robot helper for that teacher. It reads all the forms in seconds and writes down "Riya can bowl, because her form says took 12 wickets". Then it puts the students in order for the job. The teacher still makes the final choice. The robot only helps.

What recruiters will be able to do

Manage job roles

Create a job. AI pulls out the must-have skills, nice-to-have skills, domain and years of experience from the job description.

Process resumes

Upload one or a thousand. Each becomes a profile, with every skill marked stated or inferred.

Rank and search

See applicants ranked per job, with the reason behind every point. Or ask in plain English: "React developers with ERP experience, 3+ years".

Run the hiring flow

Move candidates through stages (new → shortlisted → interview → offer), add notes and notify the team.

Three ideas that make the matching trustworthy

0.2The architecture: every part and how they connect

The finished system has four layers. Every box either scales to zero or charges only per request, so it costs almost nothing while nobody is using it.

In simple words

Think of a restaurant:

  • The dining room is the website you see. That's the presentation layer.
  • The waiter takes your order to the kitchen. That's the API layer.
  • The kitchen cooks, step by step. That's the processing layer.
  • The fridge and pantry store the food. That's the data layer.

In a normal restaurant you pay staff even when it's empty. In our "serverless" restaurant, staff appear only when a customer walks in, and you pay only for the minutes they work.

0.3The journey of one resume

When a recruiter uploads a resume, eight steps happen automatically, and nobody has to press another button.

In simple words

It's like posting a parcel. You drop it in the post box (S3). The post office's alarm rings: "new parcel!" (EventBridge). A worker follows a checklist card (Step Functions): open it, read it, sort it, label it, file it. If a step fails, the card says "try again in a minute". If it keeps failing, the parcel goes to the "problem shelf" (dead-letter queue) for a human to look at.

Technical view

The browser never sends the file through our API. It uses a presigned URL: a short-lived, single-purpose link to S3. That keeps big files off Lambda, which has request-size limits, and keeps the bucket private. S3 emits an Object Created event, an EventBridge rule starts a Step Functions state machine, and each state retries with exponential backoff when Bedrock throttles.

0.4How a match score is built

AI reads the resume, but plain code calculates the score. That way the same resume always gets the same score, and every point can be explained.

In simple words

A school report card has subjects with different weights: maths might count more than drawing. A TalentMatch score is a report card out of 100 with five "subjects". The must-have skills count the most.

Worked example: an "Odoo Developer" job

The job needs Python, Odoo and PostgreSQL (must-have); JavaScript and eCommerce (nice-to-have); the ERP domain; 3–6 years.

Fairness rule

Name, gender, age, photo, religion, caste and marital status never enter the scorer. Sprint 9 has a test that changes a name and gender and proves the score doesn't move.

0.6How every sprint runs

Every sprint follows the same six-step learning loop, and we move on only when you can answer the check questions without notes.

Definition of done (every sprint)

  • All infrastructure is in CDK code, nothing clicked by hand
  • Unit tests and CDK tests pass
  • Deployed to dev and tested live
  • No errors in the logs during testing
  • Cost checked; still inside the $15 budget
  • Committed and tagged sprint-N, journal updated

Engineering principles

  • Serverless only: nothing charges while idle
  • Separate dev and prod stacks
  • Least-privilege permissions for every function
  • AI extracts facts; plain code scores them
  • Contact details are never sent to the AI
  • People make every hiring decision

0.11Check yourself

Try to answer in your head first, then click to reveal.

What does TalentMatch do, in one sentence?
It reads resumes, records every skill with the line that proves it, and ranks candidates against a job with a score out of 100 that anyone can check. A person makes the final decision.
Why does the AI extract skills but plain code calculate the score?
AI answers can vary slightly each time, and it's hard to explain exactly why it gave a number. Plain code gives the same score for the same input every time, every point can be explained, and protected attributes like gender or religion can be kept out completely (ADR-006).
What are the four layers of the architecture?
Presentation (CloudFront, S3, Cognito), API (API Gateway, Lambda), Processing (EventBridge, Step Functions, SQS) and Data + AI (DynamoDB, S3 Vectors, Bedrock).
Why does the browser upload resumes directly to S3 instead of through the API?
Files can be large, and Lambda/API Gateway have request-size limits. A presigned URL is a short-lived link that lets the browser put one file into the private bucket. It's faster and cheaper, and the bucket stays private.
"Deployed the application on AWS": should the system record the skill "Lambda"?
No. That's over-assuming. It could have been EC2, ECS, Lambda or Amplify. The system records only "AWS (general)" with low confidence (about 0.4). Never over-assume is one of the three core ideas.
Candidate B (an SAP consultant) got full domain marks for an Odoo job. Is that a bug?
No. SAP and Odoo are both ERP systems, so the domain part (15 points) is fully earned. But B's total is still low (49 vs 90.3) because the Odoo-specific must-have skills are missing. The domain helps, but skills decide.
What is a walking skeleton, and which sprint built ours?
The thinnest possible end-to-end version of the system, live early: browser → CloudFront → API → Lambda → logs. Sprint 1 built it. Later sprints add flesh to these bones.
Why do we avoid OpenSearch Serverless and NAT Gateways?
They charge every hour even when nobody uses them: about $175/month and $32/month. That alone would blow the $15 budget. We use S3 Vectors (pay per query) and keep Lambdas outside a VPC instead.
We changed the plan from SAM to CDK. Did the architecture change?
No. Both tools produce CloudFormation templates that create the same AWS resources. Only the tooling changed: sam deploy became cdk deploy, template.yaml became lib/talentmatch-stack.ts, and SAM policy templates became CDK grant*() calls.
Which files in our project actually run inside AWS?
Only src/api/*.py (zipped into the Lambda) and the built frontend/dist (served by CloudFront from S3). bin/ and lib/ run on your Mac and only describe resources.
What must be true before we call a sprint "done"?
Everything is in code, unit and CDK tests pass, it's deployed to dev and tested live, the logs show no errors, cost is checked, and it's committed and tagged sprint-N with a journal entry.
Why does every log group keep logs for only 7 days?
To stay inside the free tier. Logs are only useful for recent debugging in a POC, and longer retention slowly adds storage cost.
