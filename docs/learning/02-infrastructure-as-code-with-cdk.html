Infrastructure as code with AWS CDK

2.1Why infrastructure as code?

If your cloud setup lives only in clicks, nobody can repeat it, review it or undo it. If it lives in code, all three are easy.

In simple words

Building with LEGO, you can build a castle from memory, or you can follow the instruction booklet. With the booklet, anyone can build the exact same castle again, you can see exactly what changed between version 1 and version 2, and if you knock it down you can rebuild it in minutes.

Infrastructure as code (IaC) is the instruction booklet for your cloud. Our booklet is lib/talentmatch-stack.ts.

2.2CloudFormation: the engine underneath

CDK does not create resources itself. It writes a CloudFormation template, and CloudFormation does the building.

In simple words

A restaurant: you (CDK) write the order slip (the template). The kitchen (CloudFormation) reads it and cooks every dish. All dishes from one slip are one table's meal (a stack). If one dish burns, the kitchen throws the whole order away and puts the table back as it was (a rollback).

Technical view
  • A template is a JSON or YAML file listing resources and their settings.
  • A stack is one deployed copy of a template. We have TalentMatch-dev, plus CDKToolkit from bootstrap.
  • A change set is CloudFormation's preview: "here is what I will add, change or replace". cdk diff uses one.
  • Events are the live log of a deploy: CREATE_IN_PROGRESS, CREATE_COMPLETE…
  • Rollback: if any resource fails, CloudFormation undoes the whole deploy, so you never end up half-built.
  • Drift is when someone changes a resource by hand in the console, so reality no longer matches the template.
Watch out

Never change or delete a CDK-made resource by hand in the console. That causes drift, and the next cdk deploy or cdk destroy can fail. The rule: anything CDK created, change in code; remove with cdk destroy.

2.3CDK: App, Stack and Construct

CDK lets you write CloudFormation with a real programming language. Everything is a tree of building blocks called constructs.

In simple words

Think of a family tree. At the top is the App (grandparent). Its children are Stacks (parents): TalentMatch-dev and TalentMatch-prod. Their children are Constructs (kids): the table, the Lambda, the API. Each kid knows who its parent is, and that is how CDK knows which stack each resource belongs to.

Three levels of constructs

LevelWhat it isExample
L1A raw CloudFormation resource, every setting by hand. Names start with Cfn.new s3.CfnBucket(...)
L2A friendly wrapper with safe defaults and helper methods. What we use.new s3.Bucket(...), table.grantReadWriteData(fn)
L3A pattern: several resources wired together for youBucketDeployment (bucket upload + cache clear + helper Lambda)
Props, stage and tokens

Props are the settings you pass to a construct. Our stack has its own prop, stage: 'dev' | 'prod', so one class can build two different stacks (for example, prod keeps its table when deleted).

A token is a placeholder for a value that only exists after deploy. table.tableName looks like ${Token[TOKEN.123]} in TypeScript. In the template it becomes {"Ref": "TableCD117FA1"}, and CloudFormation fills in the real name, TalentMatch-dev-TableCD117FA1-1MYDSRWJRNU0A, at deploy time.

2.4bin/ and lib/: from TypeScript to real resources

bin/ decides which stacks exist. lib/ describes what is inside a stack. Neither one runs in AWS. Only src/ runs in the cloud.

bin/talentmatch.ts, line by line

This is the real file in your project today:

bin/talentmatch.ts
#!/usr/bin/env node
import * as cdk from 'aws-cdk-lib/core';
import { TalentmatchStack } from '../lib/talentmatch-stack';

const app = new cdk.App();

const env = { account: process.env.CDK_DEFAULT_ACCOUNT, region: 'ap-south-1' };

for (const stage of ['dev', 'prod'] as const) {
  new TalentmatchStack(app, `TalentMatch-${stage}`, { env,  stage });
}
LineWhat it does
#!/usr/bin/env nodeSays "run me with Node". CDK actually runs the file through cdk.json: "app": "npx tsc && npx tsx bin/talentmatch.ts" (type-check first, then run).
import * as cdkBrings in CDK's core library (App, Stack, Tags, Duration…).
import { TalentmatchStack }Brings in our blueprint class from lib/.
new cdk.App()Creates the root of the construct tree (Figure 2.3).
env = {…}Where to deploy. CDK_DEFAULT_ACCOUNT is filled in from your login (143495498376). The region is fixed to Mumbai so a wrong CLI setting can't send it elsewhere.
for (const stage of ['dev', 'prod'] as const)Loops twice. as const tells TypeScript the values are exactly 'dev' or 'prod', matching the stack's stage prop.
new TalentmatchStack(app, …)Builds one stack per stage: TalentMatch-dev and TalentMatch-prod. Defining a stack does not deploy it.
Watch out

The line cdk.Tags.of(app).add('project', 'talentmatch'); is missing from the end of this file. Without it, resources get stage tags (from the stack) but no project tag, so Cost Explorer can't filter by project. Add it after the for loop.

2.5Bootstrap: the CDKToolkit stack

Before CDK can deploy into an account and region the first time, it needs a small "workshop" there. Making it is called bootstrapping.

In simple words

Before builders start a house, they set up a site office and a storage shed for bricks. The shed stays for as long as they keep building. Bootstrap creates that shed: an S3 bucket where CDK drops your code zips before CloudFormation picks them up, plus roles that are allowed to deploy.

# Run once per account + region (we already did this)
$ npx cdk bootstrap aws://143495498376/ap-south-1

# Find the assets bucket name
$ aws cloudformation describe-stacks --stack-name CDKToolkit \
    --query "Stacks[0].Outputs[?OutputKey=='BucketName'].OutputValue" --output text
cdk-hnb659fds-assets-143495498376-ap-south-1

# Look inside: hash-named .zip and .json files from your deploys
$ aws s3 ls s3://cdk-hnb659fds-assets-143495498376-ap-south-1 --recursive --human-readable
Part of the nameMeaning
cdkCreated by CDK
hnb659fdsThe default bootstrap "qualifier", the same for everyone
assetsHolds deploy assets: zipped src/api and frontend/dist
143495498376Our account
ap-south-1Mumbai
Real story from our build

After cdk destroy TalentMatch-dev, one bucket was still there: cdk-hnb659fds-assets-143495498376-ap-south-1. The question was "can I delete it?". No. It belongs to the CDKToolkit stack, not to TalentMatch-dev, so destroy correctly leaves it alone. Deleting it would break every future cdk deploy until you bootstrap again. It costs fractions of a cent. To clean old files safely, use npx cdk gc --unstable=gc, never manual deletion.

2.7How to read a cdk diff

The diff is the single most important safety check. It tells you exactly what AWS will create, change or replace.

In simple words

Before a barber cuts, a good one shows you a picture: "this much off the top, this much off the sides". If the picture says "shave everything", you say stop. The diff is that picture.

Resources
[+] AWS::DynamoDB::GlobalTable Table TableCD117FA1          ← new
[~] AWS::Lambda::Function ApiFunction ApiFunctionCE271BD4   ← modified in place
 └─ [~] Environment
     └─ [+] TABLE_NAME: {"Ref":"TableCD117FA1"}
[~] AWS::Logs::LogGroup ApiLogs ApiLogs3D05D88B replace    ← destroyed and recreated!
SymbolMeaningSafe?
[+]New resourceusually check cost
[~]Changed in placeusually
[~] … replaceDeleted and created again (new name, data lost)stop and think on tables and buckets
[-]Deletedcheck why
IAM Statement ChangesWho gets which new permissionread every row
The "broadening" approval

When a deploy adds IAM permissions, CDK stops and asks:

Stack includes security-sensitive updates and "--require-approval" is set to 'broadening'.
Do you wish to deploy these changes? (y/n)

"Broadening" means someone is getting more access. In Sprint 2 that was table.grantReadWriteData(apiFn): check the Resource column shows our table's ARN and …/index/* only, then type y.

Real story from our build

The unnamed log group. Our first log group had no logGroupName, so CloudFormation generated one like TalentMatch-dev-ApiLogs3D05D88B-…, and aws logs tail /aws/lambda/… failed with "log group does not exist". We added logGroupName: `/talentmatch/${props.stage}/api`. On a live stack the diff would show the log group as replace, because a log group can't be renamed in place, so the old logs go. That's harmless for logs, and a warning sign for tables.

The deploy that ran before it was stopped. In the very first session, a cdk deploy was rejected in the terminal, yet TalentMatch-dev showed CREATE_COMPLETE a moment later. The deploy had already started before the stop arrived. Lesson: once you press enter, check CloudFormation, not your memory: aws cloudformation describe-stacks --stack-name TalentMatch-dev.

2.8Removal policies, tags and outputs

Three small settings that make a big difference: what happens on delete, how costs are grouped, and how you find real names after deploy.

lib/talentmatch-stack.ts
// Dev data is disposable; prod data must survive a stack delete.
removalPolicy: props.stage === 'prod' ? cdk.RemovalPolicy.RETAIN : cdk.RemovalPolicy.DESTROY,

// Tag everything in this stack with stage=dev or stage=prod
cdk.Tags.of(this).add('stage', props.stage);

// Print real names after deploy
new cdk.CfnOutput(this, 'ApiUrl', { value: api.apiEndpoint });

2.10Check yourself

Try to answer in your head first, then click to reveal.

Name three advantages of infrastructure as code over clicking in the console.
It is repeatable (same code builds dev and prod), reviewable (Git shows every change), and cleanly removable (cdk destroy deletes everything it created, so no forgotten resources keep costing money).
Does CDK create AWS resources itself?
No. CDK runs on your Mac and writes a CloudFormation template (cdk synth). CloudFormation in AWS reads the template and creates the resources.
What does CloudFormation do if one resource fails during a deploy?
It rolls back: it undoes every change from that deploy, so the stack returns to its last good state instead of being half-built.
What is drift and how do you cause it by accident?
Drift is when real resources no longer match the template, usually because someone edited or deleted a CDK-made resource by hand in the console. It can make the next deploy or destroy fail.
What is the difference between bin/, lib/ and src/?
bin/ creates the App and decides which stacks exist. lib/ defines what is inside a stack. Both run only on your Mac. src/ is application code (Python) that actually runs in AWS Lambda.
What is the difference between an L1 and an L2 construct?
L1 (CfnBucket) is a raw CloudFormation resource where you set everything. L2 (s3.Bucket) wraps it with safe defaults and helpers like grantRead. We use L2. L3 patterns such as BucketDeployment combine several resources.
What is a token? Give an example from our stack.
A placeholder for a value that only exists after deploy. table.tableName becomes {"Ref": "TableCD117FA1"} in the template, and CloudFormation fills in TalentMatch-dev-TableCD117FA1-… at deploy time.
What is the bootstrap assets bucket, and can you delete it?
It belongs to the CDKToolkit stack and holds the zips and templates CDK uploads on every deploy. Don't delete it: future deploys would fail until you re-run cdk bootstrap. Use npx cdk gc to clean old files.
In a diff, what does "replace" mean, and why is it dangerous?
The resource will be deleted and created again with a new physical name. For logs that's minor; for a table or bucket it means the data is gone. Stop and think whenever you see replace on stateful resources.
CDK asks "security-sensitive updates… broadening". What should you check before typing y?
The IAM Statement Changes table: which principal gets which actions on which resources. For our table grant, the resources should be only our table's ARN and …/index/*, not *.
What happens to the prod table on cdk destroy TalentMatch-prod?
Its removal policy is RETAIN, so CloudFormation leaves it in the account as an orphan with all its data. A fresh deploy would create a new, empty table; reconnecting the old one needs cdk import.
Why does cdk synth fail with "Cannot find asset at …/frontend/dist"?
The stack uploads frontend/dist with BucketDeployment, and that folder only exists after npm run build inside frontend/. Build the frontend first.
