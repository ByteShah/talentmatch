7.1The testing pyramid

A test is a small program that checks your real program. You want many fast, cheap tests at the bottom and a few slow, realistic ones at the top.

In simple words

Think of baking a cake. First you taste each ingredient: is the sugar sweet, are the eggs fresh? That's a unit test. Then you read the recipe card to check you wrote "2 eggs", not "20 eggs". That's a CDK test, checking the plan. Then you bake one cake and taste it: the live curl test. Finally a friend eats a whole slice at the party: the end-to-end test. Tasting sugar takes one second; baking takes an hour. So you taste ingredients often and bake rarely.

7.2How to read an error message

Most errors tell you exactly what's wrong. Beginners panic at the wall of text; experts read the last line first, then walk up.

In simple words

A stack trace is like a trail of footprints in the snow. The last footprint (the bottom line) is where the person fell. The footprints above show the path they walked to get there. Start where they fell, then look back to see which step went wrong.

Here's a real error from our build, when app.py passed message= twice to the log() function:

  1. Read the last line. TypeError is the kind of error, and "got multiple values for argument 'message'" is the reason. A function received the same argument twice.
  2. Find the lowest line that is in YOUR code. src/api/app.py, line 46. Lines inside /opt/homebrew/... or site-packages are libraries; the bug is almost never there.
  3. Compare that line with the function definition. def log(level, message, context, **fields) already has message as its 2nd parameter, and line 46 also passed message=e.message.
  4. Fix the smallest thing. Rename the extra field: error=e.message.
  5. Re-run the same test. Prove the fix with the same command that showed the error.

Watch out

An error can hide another error. Our health test said 404 != 200, but the real problem was a crash (ValueError) that the code caught and then fell through to return 404. If an error doesn't make sense, ask "did something earlier fail silently?"

7.3The debugging playbook

The first question is never "what's wrong?". It's "where did it stop?". Each place has its own tool to look at.

In simple words

If a parcel doesn't arrive, you don't guess. You check the tracking: did it leave the shop? Did it reach the city? Did the van deliver it? Software is the same. Find the last checkpoint where things were still fine, and the problem is just after it.

Technical view

Every request carries a request ID. Our log() function writes it into every line as request_id. When a user reports "it broke at 10:42", you search the logs for the 500 around that time, copy its request_id, and filter on it. Now you see only that one request's story.

The git fix, for this repo only:

$ git remote set-url origin https://ByteShah@github.com/ByteShah/talentmatch.git
$ git remote -v                # both lines must show ByteShah@github.com
$ git config --show-origin --get-all credential.helper   # gh auth git-credential here?
$ git config --local credential.helper ""
$ git config --local --add credential.helper osxkeychain
Real story from our build

The git 403 took two tries. The first time, only user.name and user.email were set, and the push failed again with the same message. The clue was in the error URL: it still said https://github.com/ByteShah/... with no ByteShah@. Read the error closely; it often shows exactly what was used.

7.5The daily start / stop checklist

Same steps every session, in the same order. That's how you stop forgetting things.

Start of session

$ cd ~/Work/labs/talentmatch
$ echo $AWS_PROFILE        # talentmatch
$ aws login
$ aws sts get-caller-identity
$ source .venv/bin/activate
$ git status               # clean?

End of session

$ python -m unittest discover -s tests/api
$ npm run build && npm test
$ git add -A
$ git commit -m "Sprint 2a: ..."
$ git push
$ npx cdk destroy TalentMatch-dev
Watch out

After cdk destroy and a fresh deploy, the API URL and CloudFront URL change. The deployed site fixes itself, because CDK regenerates config.json. Your local frontend/public/config.json does not, so copy the new ApiUrl into it.

7.6Cost safety

Serverless costs nothing while idle, but a few services charge every hour they exist. Know which ones.

In simple words

Serverless is like a taxi: you pay only for the ride. Some services are like renting a car: you pay every day it sits in your driveway, even if you never drive it. Our plan only uses taxis.

Costs money while idle: never create
  • NAT Gateway: about $32/month
  • OpenSearch Serverless: about $175/month minimum
  • Aurora / RDS: $45+/month
  • Amazon Kendra: hundreds per month
  • VPC interface endpoints: about $7/month each
  • Bedrock provisioned throughput
Free or pennies at our size
  • Lambda: 1M requests/month always free
  • CloudFront: 1 TB + 10M requests always free
  • CloudWatch Logs: 5 GB free; ours kept 7 days
  • DynamoDB on-demand: pay per request
  • API Gateway HTTP API: about $1 per million
  • S3: under $0.01 for our few MB
  • Budget alert: talentmatch-monthly at $15. It emails before you're surprised.
  • Cost Explorer weekly: Billing → Cost Explorer → group by Service.
  • Activate the cost tag once: Billing → Cost allocation tags → project → Activate. Tags only appear in Cost Explorer after this, and data takes up to 24 hours.
  • Credits / free tier: Billing → Free Tier (or Credits). The trial ends, but habits stay.
  • Destroy dev when you stop: the cheapest resource is one that doesn't exist.

7.7Security habits

Most cloud security disasters come from four simple mistakes. Avoid them from day one.

Watch out

frontend/public/config.json is not in any .gitignore yet. It only holds your dev API URL, which isn't a secret, but it changes on every redeploy. Add the line frontend/public/config.json to the root .gitignore so it stops showing up in git status.

Small commits, one tag per sprint, and the right identity per repo.

Technical view

Two different "who"s: author (user.name/user.email, written into each commit) and authentication (the credentials sent when pushing, picked by the remote URL and the credential helper: macOS keychain, or gh auth git-credential). Changing one never changes the other.

7.9The learning journal

One short entry per session in docs/journal.md. Writing it down is what turns "I did it once" into "I understand it".

In simple words

It's a diary for your brain. Tomorrow-you won't remember why the logs didn't show up. Today-you can write it down in three lines.

A good entry has four parts

docs/journal.md
## 2026-10-07 · Sprint 2a (DynamoDB + jobs API)

Learned: A scan pays for every item it reads (ScannedCount), not what it returns.

7.12Check yourself

Try to answer in your head first, then click to reveal.

Why do we have many unit tests but only a few live curl tests?
Unit tests run on your Mac in under a second, cost nothing and need no deploy. Live tests need a deploy (minutes) and real AWS. You want fast feedback for most checks, and a few live tests for what only real AWS can show, like permissions and CORS.
Which test layer would catch a missing table.grantReadWriteData(apiFn)?
Only the live layer. moto doesn't check IAM, so unit tests pass, and the CDK tests we wrote don't check the policy. The live POST /v1/jobs returns 500, with AccessDeniedException in the logs. You could also add a CDK test that checks the policy exists.
In a Python stack trace, which line do you read first, and which second?
First the very last line (error type plus reason). Second, the lowest line that points into your own code (for example src/api/app.py, line 46). The lines above that are the callers, for context.
Why did the health test say 404 != 200 when the route existed?
health returned a response dict instead of (status, body). Unpacking it crashed with ValueError, and except Exception only logged it, then fell through to return 404. A crash was disguised as "not found". The fix was to return a pair, and make the crash branch return 500.
You curl a URL and get {"message":"Not Found"}, and there's no line in your Lambda logs. Where is the problem?
In API Gateway. No route matched that method and path, so API Gateway answered by itself without calling your Lambda. Check the routes in CDK (for example, there's no DELETE route).
Why did git push still fail after setting user.name "ByteShah"?
user.name/user.email only set the author written into commits. Login comes from the remote URL plus the saved credentials, which were jash-yulara in the keychain. Putting ByteShah@ in the remote URL makes git ask for ByteShah's credentials.
What does Start directory is not importable usually mean?
The folder you passed to -s doesn't exist from your current directory, because of a wrong name (test vs tests) or the wrong pwd. Check with pwd and ls.
Why did only 2 of 6 Python tests run, with no error?
unittest only collects files named test*.py (so text_app.py was skipped) and methods inside a TestCase class (the job tests weren't indented). Neither mistake raises an error; they're silently skipped. If fewer tests run than you wrote, check names and indentation.
Which two things in your AWS account should you never delete, and why?
The CDKToolkit stack and its cdk-hnb659fds-assets-... bucket. Every cdk deploy uploads code and templates there first, so without them deploys fail until you run cdk bootstrap again. They cost fractions of a cent.
Why must you never delete a CDK-created bucket or table by hand in the console?
CloudFormation still thinks it owns that resource. The stack drifts from reality, and later deploys or destroys can fail. Always remove CDK resources with cdk destroy (or by removing them from the code and deploying).
You redeployed after destroying, and npm run dev on localhost shows "Failed to fetch". What's the most likely cause?
The API URL changed, but your local frontend/public/config.json still points to the old one. Copy the new ApiUrl output into it. (The deployed CloudFront site is fine, because CDK regenerates its config.json.)
Which services in our plan's "never create" list would charge even if nobody used them?
NAT Gateway (~$32/month), OpenSearch Serverless (~$175/month), Aurora/RDS ($45+/month), Kendra, VPC interface endpoints (~$7/month each) and Bedrock provisioned throughput. They charge per hour of existence, not per request.
